## Project summary

MineCorp is a fictitious Minecraft company that turns raw materials into higher-value products.

Objectives:
1. Demonstrate how Neo4j, context graphs, GraphRAG, Neo4j Agent Memory and an [Enterprise] Knowledge Layer can store complex processes and current world state.
2. Create an agent that helps employees (players) navigate the world and answer questions about MineCorp.
3. Present the project as a "fun" demonstration of how complex systems and domains can be supported by Neo4j and knowledge layers.

Deliverables:
1. Knowledge Layer describing world/server state, crafting/process mechanisms, and advice drawn from minecraft.wiki articles.
2. An agent that answers questions about MineCorp.

- 2026-10-14 Agent memory with neo4j-agent-memory (owner's request; built and committed 2026-10-16; [docs/agent-memory.md](docs/agent-memory.md)). Configurable: `AGENT_MEMORY=local` (default: history in the process only) or `neo4j`, with `AGENT_MEMORY_DATABASE`, `AGENT_MEMORY_TRACES` (on), `AGENT_MEMORY_EMBED` (off) and `AGENT_MEMORY_EXTRACT` (off, long-term entity extraction). `agent/minecorp_agent/memory.py` is the integration: the in-process `History` stays the always-on cache the book is built from, and every run is also written, off the request thread and never waited for, as short-term messages (a `Conversation` per player uuid; the answer's sources are JSON in its metadata) and a reasoning trace (steps and tool calls) for EVERY run, failed ones too (`success: false`). When the cache has nothing for a player (after a restart) the book is rebuilt from memory. Memory never costs the player an answer: failures are logged, Neo4j being down is retried after a minute, at most 100 writes may wait, a read gives up after 8 s. The library (v0.7, async only) runs on a thread with its own event loop. **Decision (owner): memory is written to the SAME database as the game graph by default**, because a separate database cannot be linked to nodes already in the graph (long-term memory to items and mobs); so `build-graph` wipes memory too, which the owner accepted; a separate database stays available through `AGENT_MEMORY_DATABASE`. ## Design principles from the Neo4j posts (build should reflect these)

From "The knowledge layer for enterprise AI":
- KL = shared, governed substrate between data and agents. "Lighter agents over a smarter shared substrate": keep knowledge in the graph, not in agent prompts/code.
- Three components: **ontology** (technical, domain, business-process, policy, organisation layers), **enterprise data** (instantiates the model; queried in place or materialised), **memory** (every run leaves a decision trace).
- Request flow: interpret intent against the model -> pick authoritative source -> generate translated query -> enforce policy/access -> capture decision trace.
- Build hybrid: bottom-up LLM-assisted discovery, top-down governance. LLMs propose mappings, humans ratify.
- Federated ownership; the layer improves each time it is used.

From "The knowledge layer for enterprise: Processes":
- Process schema: BusinessProcess -> BusinessActivity -> BusinessTask (three levels; tasks are the delegatable unit). Role (not Person) performs tasks.
- Relationships: PERFORMS, OWNS (one owner per process), NEXT, HANDOFF_TO, ESCALATES_TO.
- Routing is data: NEXT carries condition, outcome, isDefault.
- Extracted processes are *candidates* with source, extraction date, confidence; humans confirm before they are canonical.

Implications for MineCorp (proposed, not yet agreed):
- "Data stays external": recipes from the server JSON and live state from the server are the authoritative sources; the graph maps to them and holds summaries (matches the leaning on world state).
- MineCorp processes (e.g. ore -> ingot -> tool) map to Process/Activity/Task; players/NPC roles map to Role. Vanilla recipes are the underlying task inputs/outputs.
- Wiki-derived advice and any LLM-extracted links are *candidates* with source/confidence until the human approves.
- Every agent answer should write a decision trace (what was asked, which sources/queries used) to memory.
- Policy/organisation layers have a light-weight analogue (e.g. which player may see which data); decide later if needed.

**Since v0.7 (see the decisions log and docs/ontology.md):** the world (v0.10), trades (v0.12), enchantments (v0.13) and `USES_STATION {optional}` are built; the build order is recipes, actions, world, enchantments, trades, model, routes, wiki, links (`scripts/build-graph`). [model/ontology.yaml](model/ontology.yaml) is the model as a Neo4j Ontology Graph Specification, checked against the built graph by `tests/loader/test_ontology_spec.py` (the agent memory graph is the library's and is not in it). The Neo4j skills `neo4j-ontology-skill`, `neo4j-agent-memory-skill`, `neo4j-modeling-skill` and `neo4j-cypher-skill` are in `.claude/skills/` (see `.claude/skills/SOURCE.md`).

Loader (Python) and local Neo4j (docker-compose.yml): see [loader/README.md](loader/README.md). Full graph loaded with ontology v0.4 on 2026-10-02 for review.

## Architecture

[docs/architecture.md](docs/architecture.md) (v0.2, decisions agreed). Summary: thin Java plugin -> plain HTTP -> Python agent service (own process, hand-written tool-calling loop, OpenAI model, no framework) -> purpose-built read-only graph tools (`get_recipe`, ...) over Neo4j. Live-Minecraft tools and event ingest come later; MCP is deferred (the core stays transport-neutral so `ask` can be exposed as MCP later). Runs locally; plugin-to-service auth is a shared secret.

## Agent service

[agent/](agent/): Python FastAPI service with a hand-written OpenAI tool-calling loop (`agent.py`) and read-only graph tools: `find`, `list`, `get_recipes`, `what_do_i_need`, `get_uses`, `members`, `rank_recipes`, `how_to_get` (mine, kill, shear, trade), `describe`, `where_to_find`, `get_process` (`processes.py`), `search_wiki` and `read_section` (wiki); code in `tools.py`, `names.py`, `listing.py`, `world.py`. Also in the package: `sources.py`, `graphs.py`, `book.py`, `history.py`, `sessions.py` (each player's current conversation), `conversation.py`, `memory.py`, `enchantments.py`, `budget.py`. Default model `gpt-5.4-mini` (`OPENAI_MODEL`). Each question writes a decision trace to `agent/logs/traces.jsonl` (git-ignored; writing traces to the graph comes later). Run with [scripts/start-agent.ps1](scripts/start-agent.ps1); details in [agent/README.md](agent/README.md). `what_do_i_need` returns an ordered `steps` list plus a `gather` list; `get_recipes` and `what_do_i_need` include an `overview` (craftingSteps, chainLength, baseMaterials, stations). Quality check: `cd agent; python -m evals.run_evals -v` (72 questions as of 2026-10-25). `rank_recipes` reads route properties stored on `Item` by `python loader/compute_routes.py` (run it after every graph load; ~10 s). Hardest by that metric: glazed terracotta (8 steps) then the netherite tools (7 steps). OpenAI key, `AGENT_SHARED_SECRET` live in `.env`.

## Plugin

[plugin/](plugin/) is the thin Paper plugin (Maven, Java 25, `paper-api 26.2.build.129-stable`, kept in step with the server build). `/agent <question>` POSTs to the agent service asynchronously with a shared secret; `/agent-explain` (permission `minecorp.explain`) posts the player's uuid to `/explain` and opens the returned book (links as `open_url`, contents lines as `change_page`). Build and install with [scripts/build-plugin.ps1](scripts/build-plugin.ps1) (copies the jar to `server/plugins`). How to build and use it: [plugin/README.md](plugin/README.md). `/agent-clear` (permission `minecorp.clear`) starts a new chat, and a player who joins starts one too (`PlayerJoinEvent` calls `POST /clear`). Tested on a running server and in a real client by the owner (`/agent`, `/agent-explain`; confirmed 2026-10-18); `/agent-clear` and the join listener have JUnit and end-to-end tests (the console is refused) but have NOT been tried in a real client.
